= anchor: specification

This document defines anchor.

It says what anchor does. It also says what anchor deliberately does not do.

This document is versioned separately from the implementation. It was written
before the code. The code has now caught up with it: every section marked `v1`
is built.

Each section has one milestone:

v1:: Required before the first tagged release.
later:: Desired, but deferred. Specified only far enough to leave room.
non-goal:: Will not be built. Listed so the decision is explicit.

This file uses only the AsciiDoc subset that cl-adoc parses. anchor must be
able to render its own specification.

== Thesis

anchor is a static site generator for AsciiDoc. It is written in Common Lisp
and built on cl-adoc.

The build operates on documents, not on strings.

cl-adoc parses a document into a tree and renders that tree separately. anchor
uses the tree. Titles, dates, summaries, headings, link targets, and image
references come from the parsed document. They are not recovered from rendered
HTML. They are not duplicated into front matter.

These consequences are part of the design. They are not separate features:

* No front matter. The document is the metadata.
* No `<!--more-->` marker. Excerpts are subtrees.
* No HTML post-processing pass. Nothing uses regexes on rendered output.
* Link and media checking is a tree walk, not a parse of the result.

The second commitment is thinness. anchor should be readable in an afternoon.
When a feature can be replaced by a convention, the convention wins.

== Scope and freeze

Status: v1

This document defines 1.0: every section marked `v1`.

All `v1` sections have shipped. anchor is therefore finished, and the freeze
is now in force.

Finished means feature-frozen. anchor takes bug fixes and changes required to
track cl-adoc's released interface. It does not take features. The Lisp
interface is settled on the same terms.

Sections marked `later` are not promises. Promoting one requires a new version
of this specification. That should be rare.

Sections marked `non-goal` are permanent.

anchor has no privileged consumer. The author's site uses anchor on the same
terms as every other site. No site's requirements reopen a non-goal.

The freeze is written down so that it can be checked. Before 1.0, the check
was the number of unbuilt `v1` sections. After 1.0, the check is simpler: a
change is allowed only when it is a bug fix or a required response to a
released cl-adoc change.

== Non-goals

Status: non-goal

These will not be built. Users who need them should compose anchor with other
tools.

* Plugin system. Layouts and emitters are ordinary Lisp functions in the
  user's own code. That is the extension mechanism.
* Theme gallery or theme package format. A theme is a CSS file.
* Asset pipeline: bundling, minification, transpilation, SCSS, or LESS.
* Image processing: resizing, format conversion, or responsive variants.
  anchor copies bytes.
* Internationalisation and translation workflows.
* Shortcodes, or any macro layer above AsciiDoc. cl-adoc's SPEC.adoc defines
  the input language.
* Data-file cascades, content collections, or a query language.
* Deployment. anchor produces a directory. rsync, git, or CI can put it on a
  host. That is out of scope.
* Comments, analytics, or any runtime service.
* CDN configuration, cache headers, or edge rules.

== Terminology

document:: A parsed cl-adoc tree plus its source path.
page:: A document that will be written to the output tree at a URL.
asset:: A file copied to the output tree without changes.
bundle:: A directory that contains `index.adoc` and usually its media.
site:: The whole graph: every page, asset, and relation between them.
emitter:: A function from a site to a list of output files.
layout:: A function from a page and a site to an HTML tree.

== Site layout

Status: v1

=== Source tree

The filesystem is the data model. Directory structure is URL structure. There
is no permalink configuration and no slug field.

----
mysite/
  _anchor.lisp
  _media/
    portrait.jpg
  index.adoc
  about/
    index.adoc
  posts/
    _anchor.lisp
    index.adoc
    2026/
      writing-cl-adoc/
        index.adoc
        parser-tree.png
      anchor-design/
        index.adoc
        pipeline.svg
        repl.gif
  style.css
----

=== What is a page

A directory that contains `index.adoc` is a page. Its URL is its path relative
to the source root, with a trailing slash.

----
posts/2026/anchor-design/index.adoc  ->  /posts/2026/anchor-design/
index.adoc                           ->  /
----

`.adoc` files not named `index.adoc` are not pages. Discovery ignores them.
Documents can still include them.

This makes a section a first-class object. A directory can be both a page and
a parent of pages. `posts/index.adoc` is the archive page. Its children are
its posts. No configuration declares that relationship.

=== Media

Media colocates with the page that uses it. A reference resolves page-local
first. Then anchor walks up the tree looking for `_media/`.

----
image::pipeline.svg[]          resolved in the bundle
image::_media/portrait.jpg[]   resolved by walking up
----

Colocation is the default because it makes a post and its media one movable
unit. It also keeps references short and prevents naming collisions.

`_media/` is for assets shared by a subtree. It uses the same parent-to-child
walk as configuration. anchor has one cascade rule, and both features use it.

The media walk is the only place anchor resolves a name by searching. It
stays. Without it, configuration would cascade upward but media would not.
That would create two rules where this document claims one.

A written-out relative path is also fragile. It is the first thing to break
when a bundle moves.

The walk must be visible. `check` reports what every reference resolved to, so
the search can be read instead of assumed.

=== Reserved names

Any file or directory whose name starts with `_` is reserved and is not
written to the output tree.

The exception is `_media/`. Referenced files inside `_media/` are copied.

Currently reserved:

`_anchor.lisp`:: Configuration for this directory and below.
`_media/`:: Shared assets for this directory and below.
`_site/`:: Output. Never read.

=== Hidden names

Any file or directory whose name starts with `.` is hidden. Hidden names
belong to other tools, such as `.git/` and `.DS_Store`. anchor does not
discover, copy, check, or watch them.

Without this rule, a site kept in git would publish its `.git/` directory with
every build.

A site that needs a dotfile in its output, such as `.well-known/` or
`.htaccess`, adds it when it deploys. Deployment is out of scope.

=== Large media

Status: later

Files that should not live in git are declared in a manifest. The manifest
maps logical names to a remote base URL.

anchor rewrites matching references at build time and verifies nothing.
Synchronising the remote store is the user's job. It belongs in a Makefile.

== Configuration

Status: v1

`_anchor.lisp` may appear in any directory. It is ordinary Lisp. anchor loads
it, evaluates it, and merges its result parent to child. A subdirectory can
therefore override its ancestors without a central registry.

Every form in the file is evaluated in order. The value of the last form is
the configuration. The configuration is a plist.

[source,lisp]
----
(list :title      "johndoe"
      :base-url   "https://example.com"
      :author     "John Doe"
      :layout     'my-site:article
      :feed-limit 20)
----

The file is evaluated instead of read as data so earlier forms can do work.
For example, they can define the layout function named by the `:layout` key.

That is why the file is Lisp, not an ini file.

anchor loads and evaluates code from the source tree. The source tree is
assumed to be yours. anchor is not a sandbox and does not try to be one.

== The document

Status: v1

anchor calls cl-adoc. It does not reimplement any part of cl-adoc.

[source,lisp]
----
(adoc:parse-file path)
(adoc:document-title doc)
(adoc:document-attribute doc "date")
(adoc:document-headings doc)
(adoc:document-references doc)
(adoc:document-uses-stem-p doc)
(adoc:render-html doc)
----

Required attributes on a page:

`:date:`:: ISO 8601. When every other page in the section has a date, a page
  without one is a `missing-date` error. Otherwise the page is undated and is
  excluded from chronological listings.

A dated section is not declared. A section is dated when its other pages are
dated. The evidence comes from siblings, so no configuration is needed.

A root can contain a dated `posts/` section and an undated `about/` section.
That is not mixed. Neither section index needs a date.

A `posts/` section where every entry but the newest has a date is different.
That is exactly when a date was forgotten instead of deliberately omitted.

Optional attributes anchor reads: `:tags:`, `:description:`, `:draft:`.

The document title is the AsciiDoc title. There is no `title:` key in
configuration or anywhere else.

=== Drafts

A page with `:draft:` is a draft. There is no `_drafts/` directory and no
future-date rule.

The attribute wins because the document is the metadata. A directory would put
publication state in the filesystem, where no other page metadata lives. It
would also hide a draft's real URL until publication.

A future `:date:` would make the build depend on the time it ran. `:date:`
already has a job.

Drafts are excluded from the site graph, not only from the output. A
published page that links to a draft therefore has a `missing-reference`, and
anchor reports it.

`anchor serve` includes drafts. `anchor build` excludes them unless `--drafts`
is given. The point of a draft is to read it at the URL it will keep.

=== Excerpts

The excerpt of a page is its preamble. If it has no preamble, the excerpt is
its first paragraph node. The excerpt is rendered as a subtree.

There is no marker, no attribute, and no truncation of rendered HTML.

=== Content-derived output

When a document can answer a question about itself, anchor asks the document.
The author does not declare the answer twice.

`page-uses-stem-p` reports whether a page contains mathematics.
`page-description` returns the author-written `:description:` or, when absent,
the page excerpt as prose.

anchor stops at the answer. It ships no math renderer because it ships no
JavaScript. A layout decides what to do when a page contains mathematics.

The principle is this: the document tells the layout what it needs. anchor
does not act on that need by itself.

== The site graph

Status: v1

The graph is built once. This happens after all documents are parsed and
before anything renders.

The graph answers:

* Chronology: pages in date order, plus each page's predecessor and successor
  within its section.
* Sections: each page's parent, children, and ancestors.
* Taxonomy: tags to pages, and pages to tags.
* References: which pages reference which assets and pages, plus the inverse.

The reference relation is all of media management. It is computed from
`document-references`. It makes every integrity check in this document a
hash-table lookup.

=== Incremental builds

Status: later

The reference relation is also the dependency graph. Incremental builds are
deferred, but must not be designed out.

The graph is the mechanism. v1 rebuilds everything only because rebuilding
everything is fast enough at blog scale.

== Layouts

Status: v1

A layout is a function from a page and a site to an HTML tree as
s-expressions.

There is no template language. Common Lisp is the template language.

[source,lisp]
----
(defun article (page site)
  `(:article
    (:h1 ,(page-title page))
    (:p :class "meta" (:time :datetime ,(page-date page)
                             ,(page-date-human page)))
    (:raw ,(page-body-html page))))
----

`(:raw ...)` inserts cl-adoc's rendered HTML without escaping. It is the only
escape hatch, and it exists for that exact purpose.

Layouts are selected by the `:layout` key. They therefore inherit through the
configuration cascade like everything else.

How a section lists its children is a layout concern. There is no listing key,
sort key, or children key.

A section that wants a different index names a different `:layout` in its own
`_anchor.lisp`. That is already the per-section override because `:layout`
cascades. A second mechanism would be one mechanism too many.

=== Serialisation

anchor serializes the HTML tree itself. It does not depend on an HTML
generator library.

The reason is not line count. A library would win there.

The reason is data shape. Layouts return data. Head-tag composition is a list
of functions that return element forms. A list of forms can be built,
filtered, and tested.

The available generators here are macros that emit code at compile time. That
is a different shape and does not compose the same way.

Escaping happens once, in the serializer, on text that has never been part of
a markup string. `(:raw ...)` is the documented exception and the only one.

=== Emitted HTML

anchor's default layouts emit semantic, class-light HTML: `article`, `h1`
through `h6`, `time` with `datetime`, `nav`, `footer`, `figure`, and
`figcaption`.

This is an obligation, not a preference. A stylesheet alone must be able to
restyle the site completely.

If a default layout requires wrapper elements and a class on every node, the
layout is wrong.

== Styles

Status: v1

A stylesheet is a CSS file the user writes. anchor copies it. anchor does not
generate, compile, bundle, minify, fingerprint, or inline CSS.

A theme is one CSS file and, optionally, one layout function.

Every default layout emits these elements in `head`:

* `meta name="viewport" content="width=device-width, initial-scale=1"`
* `meta name="color-scheme" content="light dark"`

Light and dark mode belong to the stylesheet. Use custom properties and one
`prefers-color-scheme` block.

anchor ships no theme toggle and no JavaScript for one.

== The article shape

Status: v1

The default article page contains, in order: title, date, body.

The body is the document body in document order.

The byline is not repeated on each page. On a single-author site, it is noise.
The date is what a reader needs to decide whether a technical post is still
true.

The author belongs in the site footer and in feed metadata.

== The front page

Status: v1

The front page shows the most recent page with its excerpt. It then shows a
compact list of all remaining pages as title and date, most recent first.

Full articles are not repeated on the index. Page weight is one reason.
Duplicate heading IDs are another.

cl-adoc emits deterministic heading anchors. Two full articles on one page can
therefore produce duplicate element IDs. The excerpt avoids that by
construction.

List rows contain title and date only. A dated list of titles is the densest
useful index.

Pagination is Status: later. Until a site is large enough to need it, one page
is the archive.

== Emitters

Status: v1

An emitter is a function from a site to a list of output files.

Every derived artifact in anchor uses this interface. None of them is a
subsystem.

[source,lisp]
----
(defun atom-feed (site)
  (list (output "feed.xml" (render-feed site))))
----

Shipped in v1: Atom feed, `sitemap.xml`, `robots.txt`, and one `/tags/` page
that lists every tag with its pages grouped below it.

Shipped later: per-tag pages, search index as JSON, redirect map.

anchor ships one `/tags/` page, not one page per tag. Output filenames are
stable. A per-tag page creates a URL that must remain valid, including for tags
that turn out to be mistakes.

A site that wants per-tag pages before anchor ships them writes an emitter.
That is what the interface is for. That is why per-tag pages are deferred
rather than missing.

Head-tag composition applies the same idea to `head`: a list of functions from
page and site to element forms.

That list contains `title`, `meta description` from the page's
`:description:` or excerpt, canonical link, and Open Graph and Twitter card
tags. A site can replace the list wholesale.

The canonical link and Open Graph tags are absent when a site has no
`:base-url`. This follows the same rule as the feed: useful values are
absolute URLs. A card built on relative URLs is worse than no card.

The head list and emitter list are anchor's entire answer to search-engine and
social-preview concerns. There is no SEO feature.

=== robots.txt and crawler policy

anchor emits `robots.txt` and, optionally, `llms.txt`.

Both files are advisory. Compliant crawlers honor them. Non-compliant crawlers
do not.

Enforcement belongs at the server or edge. anchor does not touch that layer
and will not configure it.

The set of user-agent strings worth naming changes faster than this
specification. This document does not enumerate them.

== Output

Status: v1

Output is written to `_site/`.

Assets are copied there instead of served from the source tree. The output
directory is therefore self-contained, the development server has one root,
and "orphan" has one meaning.

Output filenames are stable. Assets are not content-hashed. For a personal
site, permanent URLs are worth more than cache busting.

Content hashes are computed for identity, not for naming. They are used to
detect duplicates.

== Build behaviour

Status: v1

Build problems are signalled as conditions with restarts. They are not
collected into a list of strings.

Conditions:

`missing-reference`:: A link or image target does not exist.
`missing-date`:: A page that requires a date does not have one.
`unreadable-document`:: cl-adoc could not parse a page.
`unreadable-configuration`:: An `_anchor.lisp` did not read or did not
  evaluate.
`usage-error`:: The command line was not valid for anchor.

Restarts are offered where they are meaningful. `skip-page` is available
around each page as it is read. `continue` is available around each problem
the build reports.

Two pages resolving to one URL has no condition because it cannot happen. A
URL is a directory path. Two directories cannot share one path, so the
filesystem rules it out.

The policy is bound at the top of the build:

`:strict`:: Any condition aborts. CI uses this.
`:permissive`:: Report and continue. `--force` uses this.
`:interactive`:: Enter the debugger at the offending node. This is the
  default when building from a REPL. It is one reason anchor is written in
  Lisp.

== Command line

Status: v1

`anchor build`:: Build the site into `_site/`. Drafts are excluded unless
  `--drafts` is given.
`anchor serve`:: Build, serve `_site/`, and rebuild on change. Drafts are
  included.
`anchor check`:: Run integrity checks and exit non-zero on failure.

=== check

`check` reports from the reference relation:

missing:: Referenced, but does not exist.
orphans:: Exists, but is referenced by nothing. Reported, never deleted.
duplicates:: Identical content under different names.
weight:: Total bytes per page and the largest assets.
resolutions:: Every reference and the path it resolved to.

`orphans` and `weight` are the checks that matter in year three. Both are a
walk plus a hash table.

`resolutions` keeps the `_media/` walk honest.

== Development server

Status: v1

`anchor serve` holds the site graph in the Lisp image. Recompiling a layout at
the REPL affects the next request.

[source,lisp]
----
(anchor:page "posts/2026/anchor-design")
----

That returns the page object. Rebuilding one page is a function call.

This is not a hot-reload feature. It is what having an image gives you. It is
documented here so that it does not get designed away.

== Compatibility

Status: v1

Implementation:: SBCL. Other implementations are untested, not unsupported.
Build:: ocicl, as with cl-adoc.
Version:: 1.0. The freeze is in force. The Lisp interface changes for a bug
  or for cl-adoc, and not otherwise.
License:: MIT.

anchor tracks cl-adoc's released interface. It does not depend on cl-adoc
internals. It does not work around cl-adoc bugs; those get fixed upstream.
